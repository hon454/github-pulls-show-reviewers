## Real old-profile upgrade

The committed [standalone probe](../../tests/helpers/release-upgrade-probe.ts)
pins the actual published v1.15.0 digest/size. It does not replace old execution
with old-shaped data injected into new code.

1. Extract and launch **v1.15.0** in a newly-created persistent Chromium profile.
   Observe old manifest version and absence of a language selector. Seed two
   synthetic accounts (all/selected installation coverage) in that old runtime.
   Exercise the old UI to save all three non-default display values: badges off,
   usernames on, open-PR-link filter off.
2. Compare raw settings, both profile/auth/installation records and preferences;
   retain only booleans and SHA-256 digests, never token values. Close Chromium.
3. Replace only the same disposable unpacked path with exact checked **v1.16.0**
   ZIP members. Restart the same profile and assert unchanged extension ID.
   Every raw record and digest is retained. `language` remains absent in raw old
   preferences; the new UI correctly derives **Auto**, without rewriting them.
4. Select Traditional Chinese, verify only the language field is added and
   native metadata is unchanged. Close the process and launch the same profile
   again: both accounts, all display values, raw auth records and manual language
   survive. Original published ZIP stays unchanged.

The probe passed. Its initial fixture attempts used Playwright `setChecked`,
whose immediate post-click assertion raced the old controlled input's async
storage commit. The final probe performs a user click, then awaits both durable
storage and checked state. This is a probe synchronization correction, not an
extension-runtime fix. The disposable profile is removed; sanitized results and
the reproducible script remain. A closed loopback proxy blocks startup egress;
HTTP(S) interception aborts all attempted external requests. No live sign-in or
private API traffic is used. This validates a real unpacked-path upgrade, **not**
Chrome Web Store signed automatic update delivery.
